# 业务驱动重构

**核心信念**：代码乱，往往不是工程师偷懒，而是业务本身被补丁糊乱了。不先把业务理清楚就动手重构，只是在整齐地整理垃圾。

## 诊断透镜

阅读代码时套用这些透镜。每个透镜命名了一类业务意图与代码现实之间的错位。

**Patch Layer（补丁层）** — 后来追加的需求，以条件分支和特殊处理的形式附着在核心逻辑上。特征：读代码时能"看到时间"——先有一段清晰的逻辑，后面不断追加 else/if。信号：
- 条件链（`if type == "A" ... else if type == "B" ...`）
- "Also" 类注释（`// Also update inventory`）
- 函数名带 "And"（`createOrderAndNotifyAndLog`）
- 没有业务解释的魔数
- 被注释掉的代码块（前一个人也不敢删）
- 变量名与实际用途不符

**Intent Drift（意图漂移）** — 代码行为已偏离原始业务意图。功能能用，但代码说的"故事"和业务需要的"故事"对不上。信号：变量 `pendingOrder` 实际存的是"已支付未发货"。

**Ghost Logic（幽灵逻辑）** — 代码仍在执行业务上已不需要的操作。特征：问"这段能删吗？"没人能回答。

**Logic Fragmentation（逻辑碎片化）** — 一条业务规则散落在多个文件中。每个碎片单独看都不表达完整业务含义。

**Business Invariant（业务不变量）** — 无论代码怎么改都不能破的规则。大量 bug 的根源是补丁破坏了不变量。

**Core Flow vs Exception Flow（核心流程 vs 异常流程）** — 主路径（>80%）vs 边缘情况。危险信号：异常流程的代码量和复杂度压倒核心流程，读者迷失在边缘情况里。

## 错位分类

**幽灵逻辑** — 代码在做业务已不需要的事。

**碎片化** — 一条规则散布多处，没有一处说清完整业务含义。

**不变量被架空** — 代码结构上允许了绝不该发生的事。

**补丁颠倒主次** — 异常流程压倒核心流程。

**命名背叛** — 代码命名和业务术语对不上。

## 执行

考古 → 确认 → 错位分析 → 理顺方案。

**考古**：从代码和 git 历史重建业务地图。追踪每个入口的 happy path 和分支，标记所有补丁信号。

**确认**：向用户呈现发现。标出低置信度项——那些光看代码无法确定业务意图的地方——逐项确认。

**错位分析**：用上述透镜给每一项错位归类。

**理顺方案**：为每个错位提出方案、迁移路径、优先级和风险。核心原则：**先理顺结构，不改变行为**——每一步小到可以在测试保护下完成。

## 完成标准

1. 业务地图已从代码重建并得到用户确认
2. 所有业务与代码的错位已识别并归类
3. 每个错位已有理顺方案，优先级和风险已讨论
4. 新澄清的业务概念和已确认的不变量已记录

## 危险信号

- "直接重构就行，不用管业务"——拒绝。不理解业务就动手，是在整齐地制造 bug。
- git 历史混乱——如实告知：会有更多低置信度发现。
- 业务不变量既无代码约束也无测试保护——高优先级，先补测试再重构。

## 适用边界

最适合业务逻辑反复打补丁、"为什么这么写"已经不清晰的场景。跳过：业务逻辑清晰的结构重构、纯技术债、新功能开发、或已明确知道要改什么的情况。
